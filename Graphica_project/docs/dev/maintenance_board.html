推奨の実施順 ORDER

上から順に進めます。項目の色は状態(灰=未着手、青=対応中、緑=完了)。「次はここ」は未完了の項目が残る最初の段階です。K(ついでの改善)は見つけ次第、どの段階でも直します。

    作業ルールと引き継ぎ HANDOFF

    別のセッションで作業を始めるときは、ここと Graphica_project/docs/dev/CURRENT_STATE.md を先に読んでください。

    どの項目にも共通して行うこと(ユーザー指示、2026-09-18)

    各項目の作業では、その項目の本題に加えて、触ったファイルについて次の2つも必ず行う。

    • pip 配布に向けた整理: トップレベルに新しいモジュールを増やさない(新しいコードは I-1 後の graphica.* の配置、I-1 前なら既存パッケージの中に置く)。リソースはパッケージ内に置き resource_path() 経由で読む。カレントディレクトリに依存しない。本体の内部に依存するプラグイン向けの書き方を増やさない(G-1 の窓口を使う)。
    • コメントを最小限にする: J-1 の方針に沿って、触ったファイルの経緯・実機フィードバックの記録・項目番号の説明などを削り、「なぜそうしているか」「知らないと壊す制約」だけを残す。不要になったコード(使われていない関数・import・分岐)も同時に消す。

    ついでに見つかったアプリの改善(K、ユーザー指示、2026-09-18)

    保守性の作業中に見つけたアプリの不具合・改善点は、同じブランチでまとめて直す。見つけた時点で上の「K」に登録する(データベースの findings コレクション、doc_id は K-1, K-2…。ユーザーもボードのフォームから追加できる)。

    • 登録: title / where(ファイル:行や画面の場所)/ detail(何が起きるか・再現手順)/ sev(high・mid・low)/ size(S・M・L)/ state(todo)/ found(どの項目の作業中に見つけたか)。
    • 確認なしで直してよいもの: 挙動が明らかに誤っていて、直し方に仕様判断がなく、S サイズのもの。それ以外(見た目・操作の変更、保存形式に関わるもの、M 以上)は登録だけして、ユーザーに選択肢と推奨を示して確認してから直す。ユーザーが登録したものは、それ自体が依頼なので着手してよい(仕様判断がいる点だけ確認する)。
    • コミットを分ける: 挙動を変える修正は、リファクタリングやコメント整理のコミットに混ぜない。1 件 1 コミット(fix: …)で、再現するテストを先に書く。リファクタリングの「挙動は変わっていない」という検証を崩さないため。
    • タイミング: 直すと進行中の H/I 項目と衝突する場合は、その項目を終えてから直す。
    • 完了: state を done、note にコミットハッシュと要点。PR の本文に K の一覧を載せ、次のリリースノートに入れる。利用者向けの挙動が変わったら Wiki の該当ページも直す。

    リファクタリングの絶対条件(R、ユーザー指示、2026-09-25)

    既存のすべての機能、入力と出力の仕様、副作用、端の挙動を完全に維持する。変えてよいのはアーキテクチャ・クラスとモジュールの設計・関数の切り出し方などの内部構造だけで、これは根本から変えてよい。

    • 不具合を見つけても直さない: 分析や作業の途中で、維持すべき挙動そのものに不具合や改善点を見つけたら、その都度 K として登録し、新しい改善案としてユーザーに提案する。R のコミットでは挙動を変えない(今の挙動をそのまま再現する)。
    • 検証: R-0 の特性テスト(画面の組み立て結果・描画の画素・保存したファイル・表示の記録)が変更前と一致することで確かめる。

    着手順

    ページ上部の「推奨の実施順」を参照。

    プロジェクトの規約(既存)

    • 1 項目ごとに 実装 → テスト → コミット → push。完了したらこのボードの状態を「完了」にし、note(コミットハッシュと要点)を書き、更新後の進捗表をユーザーに表示する。
    • core/・gui/theme.py・保存形式・プラグインのレジストリなど共有の仕組みに触れる変更はフルスイート必須(scripts/run_tests_chunked.sh、約 18 分。素の pytest で全件は流さない)。
    • コストやリスクの大きい設計判断は、着手前に選択肢と推奨を示して確認する(「方針確認」の付いた項目)。
    • 挙動を変えない整理は、変更前後で同じテストが通ることで確かめる。テストが内部メソッド名に依存している場合は、テストを公開の振る舞いに合わせて直してから分割する。

    知っておくべき地雷(抜粋。詳細はリポジトリ直下の CLAUDE.md)

    • サブメニューは QMenu と menuAction() の両方を self. 属性で保持しないと PySide6 が破棄する(H-4 で必ず踏む)。
    • formLayout_3 は番号指定の insertRow が実行順に依存している(H-3 で注意)。
    • テストでモーダルダイアログが実際に開くと、チャンク実行がそこで止まったまま戻らない。止まったら CPU 時間の増加で判定する。
    • プラグインは graphica_plugin_<名前> という動的モジュール名で読み込まれ、from core.dataset import Dataset で本体を使っている(I-1 の互換で壊さないこと)。
