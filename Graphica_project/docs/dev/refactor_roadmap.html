絶対条件RULES

ユーザーの指示(2026-09-25)。R のすべてのコミットがこれを満たすこと。

維持すること
  • 既存のすべての機能、入力と出力の仕様、副作用を完全に維持する。
  • 既存のエッジケースの挙動も変えない(いまの不具合も含む)。
  • 作業中に見つけた不具合や改善点は直さずに、K として登録して提案する。直すのはユーザーが選んだあと、別の fix: コミットで。
変えてよいこと
  • アーキテクチャ、クラスやモジュールの設計、関数の切り出し方などの内部構造は根本から変えてよい。
  • 目標は、読みやすく、直しやすく、使い回しやすい構造にすること。
  • 変えていないことの証明は R-0 の特性テストで行う。refactor: コミットでは基準のファイルが 1 バイトも変わらないこと。

ブランチと統合BRANCHING

大きな変更なので master から切り離します。master に入れるのは、全段階が終わり、テストと動作確認で問題がないと確かめたあとの 1 回だけです。

必要なら緊急の修正だけV-6 で 1 回だけ統合

refactor/r<n>-…段階ごとの作業ブランチ
refactor/r0-characterizationrefactor/r2-fit-modelsfix/k20-……
取り込みの流れ
  1. 段階ごとに refactor/architecture から作業ブランチを切る。
  2. 終わったらフルスイートと特性テストを通し、PR を refactor/architecture 向けに作る(作成とマージはユーザーの承認後)。
  3. K の修正は、対応する段階の PR を取り込んだあと、別ブランチ fix/k<n>-… の別 PR にする。
  4. マイルストーンの始めに master を refactor/architecture へマージして、ずれをためない。
  5. V-1〜V-5 がすべて済んだら、ユーザーの承認を得て refactor/architecture → master の PR を作り、マージする。
決めごと
  • 元の refactor/maintainability は役目を終えた(F〜J はすべて master に統合済み)。以後は使わない。消すのはユーザーの指示があってから。
  • R の期間中、master には緊急の修正以外を入れない。入れたら次のマイルストーンの始めに取り込む。
  • CI の pull_request は今 master 向けにしか動かないので、P-2 で統合ブランチ向けにも動かす。
  • メインのフォルダ PlotterApp(master)には触らない。作業フォルダで pip install -e はしない。
