## 2. 2つのリストの性格比較

### 前回レビュー案(A)の傾向

コードベースの構造から出発しているため、**基盤・非機能要件に厚い**。

- 強かった領域: 性能(再描画スコープ、キャッシュ、スレッド)、保存形式のバージョニング、再現性(provenance)、出版品質の実務(`pdf.fonttype`)、運用(診断情報、セーフモード)、テスト戦略
- 薄かった領域: **手法別の解析(XPS/XRD/CV/DSC/NMR等)がほぼ空白**。プロット種別の網羅性、注釈・装飾の細かい機能

### Gemini案(B)の傾向

ユーザーが「やりたいこと」から出発しているため、**アプリケーション層に厚い**。

- 強かった領域: **分野特化の解析(4章の10件は独自の価値)**、プロット種別の網羅、3D、注釈・装飾、UI操作の細部
- 薄かった領域: 性能・スケーラビリティ(100件中1件のみ)、保存形式のバージョン管理(0件)、フィットの品質(誤差・重み・拘束が部分的)、運用・診断(0件)、テスト(0件)

### 相互補完の実例

| 領域 | Aの視点 | Bの視点 | 統合後 |
|---|---|---|---|
| ベースライン補正 | ALS/多項式/ラバーバンド(汎用) | Shirley/Tougaard(XPS特化) | 汎用=本体 C-308 / 特化=プラグイン P-201 |
| 有意差検定 | 検定+ブラケット注釈を1機能として | 同上 | **描画プリミティブ=本体 C-703 / 検定ロジック=プラグイン P-402** に分離 |
| 2Dマップ | データ構造・format_versionの前提を指摘 | EEM/相関行列/STFT等の用途を列挙 | 描画基盤=本体 C-508 / 用途=プラグイン P-305, P-403, P-208 |
| 軸機能 | 単位変換の第2X軸 | 軸中断・マルチY軸・関数マッピング | 全て本体 C-6 に統合(4件に拡張) |
| フィット | 誤差・重み・構造化を重視 | 拘束・残差・信頼区間を重視 | 本体 C-4 として13件に統合 |

**Bの4章(分光・物性データ解析特化)がAには完全に欠けていた領域**で、統合の最大の収穫。逆に**Aの性能・基盤層がBには完全に欠けていた**。

## 3. 本体 / プラグインの振り分け基準

### 本体に置く条件(いずれか1つでも該当)

1. **プラグインからは実装できない** — 描画エンジン、データモデル、Undoスタック、保存形式に触る必要がある
2. **分野を問わず使う** — 想定ユーザーの過半数が使う
3. **非機能要件** — 性能、安定性、配布、診断
4. **プラグインAPIそのもの** — 拡張ポイントの提供側

### プラグインに置く条件(いずれか1つでも該当)

1. **特定の測定手法・装置・分野に固有** — XPS、XRD、CV、NMR等
2. **使うのは一部ユーザー** — おおよそ3割以下
3. **重い外部依存を持ち込む** — exeサイズへの影響を隔離したい
4. **本体と異なる周期で更新したい** — 参照データベース、装置形式の追加
5. **本体の安定性から隔離したい** — 実験的な解析手法

### 判断が割れた項目と結論

| 項目 | 論点 | 結論 |
|---|---|---|
| 2Dマップ / ヒートマップ | 用途は分光特化に見える | **本体**。描画エンジンとデータモデルに触るためプラグイン不可。用途側をプラグインに |
| PCA | 統計手法だが分野横断 | **プラグイン**。追加依存なしで作れるが、使うのは一部。ただし優先度は高め |
| HDF5読込 | 汎用フォーマットに見える | **プラグイン**。`h5py`をexeに同梱するとサイズ増。使うユーザーも限定的 |
| 3D描画 | 一部ユーザーのみ | **基本描画は本体**(matplotlib同梱で追加依存なし)、**高度な機能(ライティング/ボクセル/quiver)はプラグイン** |
| LaTeXレンダリング | 仕様7章-1で「将来プラグイン」と確定済み | **プラグイン**(方針通り)。ただし差替フック C-1306 は本体側の実装 |
| Tauc plot | 極めて簡単(数行) | **プラグイン**。簡単さは判断基準にしない。分野固有性で判断 |
| 検量線・LOD | フィット機構の応用 | **プラグイン**。分析化学固有。ただし本体 C-401 が前提 |
| 動画エクスポート | GIFとMP4で依存が違う | **GIF=本体**(Pillowのみ)、**MP4=プラグイン**(ffmpegバイナリが必要) |

## 4. 最重要の発見:プラグインAPIが決定的に不足している

**プラグイン行き64件のうち62件は、現状のプラグインAPIでは実装できない。**

現状の `GraphicaPluginAPI`(仕様4.5節):
- `register_fit_function`
- `register_menu_action`

必要な拡張ポイントと、それに依存するプラグインの数:

| 必要なフック | 依存件数 | 提供できるようになるもの |
|---|---|---|
| `register_analyzer` | 33 | 手法別解析パック全て、統計、参照DB照合 |
| `register_importer` / `register_exporter` | 22 | 装置形式全て、外部連携 |
| `register_panel` / `register_dock` | 10 | 解析パックの専用UI |
| `register_plot_type` | 8 | 特殊プロット、3D拡張 |
| `register_processor` | 5 | 前処理(Shirley、スパイク除去等) |
| `register_render_backend` | 2 | LaTeX、Plotly |

### 結論

**「分野特化はプラグインで」という方針を採るなら、本体側の最優先タスクはプラグインAPIの拡張ポイント設計(C-13)である。**
これが無い限り、分野特化機能は「本体に押し込むか、実装しないか」の二択になり、本体が肥大化する。

仕様7章-1が「LaTeXは将来プラグインで提供する想定だが、フックはまだ未設計・未実装」と自認しているのは、この問題の一角にすぎない。

### 設計原則の提案:薄い本体API + 厚いプラグイン

振り分けの過程で繰り返し現れたパターンを原則化する。

> **本体は「道具」を持ち、プラグインは「使い方」を持つ。**

| 本体(道具) | プラグイン(使い方) |
|---|---|
| ブラケット注釈の描画 (C-703) | t検定を実行して`*`を配置する (P-402) |
| 汎用ベースライン補正 (C-308) | XPSのShirley背景 (P-201) |
| フィットエンジン+拘束UI (C-403) | XPSのスピン軌道分裂の拘束条件 (P-301) |
| 2Dマップ描画 (C-508) | 蛍光EEMの散乱除去と表示 (P-305) |
| カラーバー (C-501) | 相関行列の表示 (P-403) |
| 構造化フィット結果 (C-401) | 検量線からのLOD算出 (P-314) |

この形なら、本体は分野が増えても肥大化しない。

## 5. exe配布環境でのプラグイン運用という未解決課題

振り分けを進める中で、**仕様書に記載のない実務上の問題**が浮上した。

### 問題1:プラグインの導入経路

現状「`plugins/`ディレクトリに置くだけ」だが、PyInstallerでexe化された配布物では:
- `C:\Program Files\Graphica\plugins\` は書き込み権限がない
- `sys._MEIPASS`(展開先の一時ディレクトリ)は起動のたびに変わる

**対応(C-1310):** `%LOCALAPPDATA%\Graphica\plugins\` を探索対象に追加し、GUI からのインストール(zipを選択して展開)を提供する。

### 問題2:プラグインが依存パッケージを持ち込めない

exe同梱のPythonには pip が無いため、プラグインが `h5py` や `plotly` を必要としても導入できない。

**選択肢:**

| 案 | 内容 | 評価 |
|---|---|---|
| (a) 依存を本体に同梱 | よく使うものを事前に入れておく | exeが肥大化。プラグイン化の意味が薄れる |
| (b) 依存同梱形式のプラグイン | プラグインzipに wheel を同梱し、起動時に `sys.path` へ追加 | **推奨。**ネイティブ拡張のABI互換に注意が必要 |
| (c) pip版利用者限定 | プラグインは PyPI 配布版でのみ利用可 | 実装が最も楽だが、exe利用者を切り捨てる |
| (d) 純Python縛り | プラグインは標準ライブラリ+本体の依存のみ使用可 | 制約は強いが、実は多くの機能が実装可能 |

**現実的な折衷:** (d) を原則とし、需要が高い依存(`h5py` 等)だけ (a) で本体に取り込む。(b) は将来の拡張余地として設計だけしておく。

この判断は **P-1(装置形式インポータ)の実装可否を左右する**ので、C-1301 の実装前に決める必要がある。

## 9. このレポートの前提と限界

- 需要(◎/○/△)の評価は、仕様書に記載された想定用途「理系の研究・実験(分光データ、時系列測定)」に基づく推定。**実ユーザーの声があれば、特に P-3(手法別パック)の優先順位は大きく変わる**。どの測定手法のユーザーが多いかが分かれば、P-301〜P-315 の順序を確定できる。
- 工数はソースコード未確認のための概算。特に本体側の C-003(再描画スコープ)と C-004(スレッド)は、既存コードの結合度によって2〜3倍変動しうる。
- プラグインの依存の扱い(5節・問題2)は、外部の制約(PyInstallerの仕様、対象ユーザーの環境)に依存するため、実機での検証が必要。
- 参照データベース系(P-8)はライセンスの確認が必須。ICDD PDF等の商用DBは同梱・再配布できない。
